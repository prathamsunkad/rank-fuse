## Results (A100 80GB PCIe; full tables in SUMMARY.md)

Speedup = baseline / RankFuse on the same batch, median over each (r_max, step type, budget) group;
"incl." charges both sides their per-step sort / prepare amortized over 7B's 196 LoRA calls.
Run-to-run noise (rf1_fused pass 0 vs 1): median 1.000, p10-p90 0.994-1.008.

**Single adapter, rf2_ranges on sorted rows**
* vs B1: r_max 64 1.81-2.03x, r_max 128 1.61-1.96x (never slower); r_max 256 decode-only 1.52x,
  mixed steps 1.38-1.90x median but slower in 14-44% of workloads (min 0.69x).
* vs B3: 1.89-2.20x / 2.21-3.26x / 3.12-5.10x at r_max 64 / 128 / 256, never slower.
* vs B4 (bgmv on all tokens): decode-only 4.2 / 5.5 / 8.8x, prefill-heavy 17-72x.
* incl. sort / prepare changes these by at most ~0.06x.

**Single adapter, rf1_fused on random (unsorted) rows**: vs B1 1.72-2.19x (r_max 64), 1.35-1.71x
(128), r_max 256 decode-only 1.16x but every mixed step type 0.76-0.95x median (slower in 56-89%);
vs B3 1.78-2.77x everywhere, never slower.

**Multi adapter (new rf1_ma)**: vs B3-multi 2.8-4.4x / 3.4-6.0x / 2.4-7.1x at r_max 64 / 128 / 256;
vs B1-multi 7.7-23x / 6.3-17x / 1.9-9.5x; vs B4-multi-copies 2.6-24x / 3.2-37x / 3.7-24x. Never
slower than any baseline in any workload; the RF2-MA variants likewise (rf2_ma_bucketed vs B3-multi
up to 8.1x kernel-only at r_max 256).

**New kernels (2c30e56) vs `_legacy` (Stage 2)**: rf1_ma 0.93-0.96x at r_max 64 on decode-heavy
steps (1.00-1.02x prefill-heavy); 1.04-1.53x at r_max 128 and 1.13-1.36x at r_max 256. rf2_ma_segment
0.84x and rf2_ma_bucketed 0.87x of legacy on r_max 64 decode-only steps.

**Where RankFuse does not win**
1. r_max 256, prompts at r_max (`prefill_dist: all_max`): rf2_ranges vs B1 median 0.95x, slower in
   73 of 84 workloads (prompts on the decodes' own mix: 2.06-2.16x, never slower; skew_high: ~1.5x,
   11 of 84 slower).
2. r_max 256, rf1_fused on unsorted rows: every mixed step type loses to B1 (median 0.76-0.95x).
3. No reorder: if the engine cannot reorder requests and rows are permuted per LoRA call
   (index_select + index_add_, 14-814 us per call, an upper bound), `rf2_ranges+permute` loses to B1
   everywhere at r_max 64 (0.28-0.99x). Use rf1_fused there instead.
4. New multi kernels vs their Stage 2 versions at r_max 64 (above). Nothing loses to B3 or B4.

**Per-step sort / prepare (wall time, host + GPU)**: rf2_ranges sorted path (host request sort +
RangePlan) 138-218 us; rf2_index 100-120 us; B1 ~37 us; B3 530-655 us. Multi: rf1_ma 0.74-1.08 ms,
rf2_ma_bucketed 2.7-4.6 ms (its incl. speedup vs B3-multi drops, e.g. r_max 64 decode-only 3.95x ->
2.29x), B1-multi 1.4-1.9 ms, B3-multi / B4-multi-copies per-step metadata 0.6-21.5 ms (host
`torch.unique` of (adapter, rank) pairs over all tokens, as our wrappers build it; vLLM's own
bookkeeping may be cheaper).

## Assumptions

* Steps are synthetic (Tony's `serving_` / `chunked_` presets; multi: Zipf adapters, independent of
  rank). One 4096 x 4096 fp16 layer, not a model's projections.
* rf2_ranges / rf2_segment are timed on a batch generated sorted by rank: the scheduler is assumed to
  reorder whole requests (cost measured, `sort_requests_host`), not to permute rows per call.
* B3 has a padded fixed slot per (adapter,) rank tier already loaded; B3-multi / B4-multi-copies weight
  copies are built outside timing and not charged per step (persistent slots / pool).
* B4 runs bgmv on every token (see the caveat above); B4 at widths 128 / 256 uses the widened
  narrow sizes (`slora_bgmv_wide.py`, `bgmv_config.h`).
* Amortization uses the 4096 x 4096 kernel time over 168 (0.5B: 24 x 7) or 196 (7B: 28 x 7) calls;
  the models' projections are smaller, so the real prepare share is somewhat larger.
* B0 is the correctness oracle only (not timed).

## Workloads

The four step types of `rf2_mixed.yaml` (token budget = vLLM `max_num_batched_tokens`, 2048 or 8192):

| step type | lengths | what it is |
|---|---|---|
| decode only | (none) | 32 or 256 one-token decodes |
| one prompt fills | `chunked_2048_2048`, `chunked_8192_8192` | the decodes + one prompt chunk filling the rest of the budget |
| short prompts | `serving_1_2048`, `serving_2_8192` | 1 or 2 sampled prompts (log-normal, median 256 tokens), budget not filled |
| partial prefills | `chunked_2048_512`, `chunked_8192_512`, `chunked_8192_2048` | several prompt chunks of 512 / 2048 tokens filling the budget |

Synthetic; no trace behind any of it.

**Part 1 (single adapter)**: Tony's grid unchanged (`bench/configs/rf2_mixed_a100_r{64,128,256}.yaml`;
his configs untouched): 32 / 256 decodes; decode rank mix `skew_low` / `zipf_1`; prompt rank mix the
same (`null`), `skew_high` or `all_max`; request order `random` / `sorted`; pow2 tiers; 4096 x 4096
fp16; seeds 0, 1, 2. 528 workloads per r_max.

**Part 2 (multi adapter)**: `rankfuse/mixed_multi.py` (new module; existing workloads unchanged).
Each step has exactly the single-adapter step's request lengths, order and ranks for the same
parameters (it builds the same `Workload`); each request additionally gets an adapter from a Zipf
popularity (alpha 0.8 / 1.0 / 1.2) over 4 / 16 / 64 adapters, independent of rank and phase. Prompt
rank mix `null` (as decodes) or `all_max`. Batches in arrival order, a request's tokens consecutive.
4096 x 4096 fp16, shuffled pages (`PagedWeights.paged`), seeds 0, 1, 2. 1620 workloads per r_max
(`bench/configs/multi_mixed_a100_r{64,128,256}.yaml`).

**B4 on prefill-heavy steps = "S-LoRA bgmv applied to all tokens".** Real S-LoRA runs prompts (>= 200
tokens) through a separate Triton prefill kernel and uses bgmv for decode tokens only. Here bgmv
computes every token of the step, prompts included. That is a model of S-LoRA on a mixed step, not its
exact behaviour; on prompt-heavy steps it overstates S-LoRA's cost. Every B4 row in the multi-adapter
JSONL carries `b4_note: "S-LoRA bgmv applied to all tokens"`.

B4 at r_max 128 / 256: S-LoRA's bgmv is compiled with narrow sizes 128 and 256 (`bgmv_config.h`,
copied from the main checkout's A100 sweep work); the single-adapter B4 takes them through
`rankfuse/baselines/slora_bgmv_wide.py` (widens `slora_bgmv.NARROW_SIZES` in the sweep process only),
the multi-adapter B4 through `slora_bgmv_multi.py` (also copied from the main checkout).

## Sorting (rank order) — outside the timed region for every kernel

* `rf2_ranges` / `rf2_segment` need rows physically sorted by rank. With `request_order: sorted` the
  batch is **generated** sorted (`rankfuse.workloads.make_batch` orders whole requests by rank, as a
  scheduler would), before any timing. Every implementation, baselines included, is timed on that
  same sorted batch, and on the same `random` batch for the other order; speedups always compare two
  kernels on the same batch. No physical permutation of x / out is timed or charged. On `random`
  order `rf2_ranges` falls back to one `rf1_fused` launch.
* `rf2_index` (single) and every multi-adapter kernel sort or group tokens by an index list built in
  their `prepare` (`torch.argsort` on the GPU for `rf2_index`; `build_meta` / `BucketPlan` for
  multi), which runs outside the CUDA graph. `prepare_us` in the single-adapter CSV records it (host
  wall time, eager), not added to `median_us`.
* The baselines' per-step metadata (B1 r_b, B3 `LoRAKernelMeta`, B4 pool and entries) is likewise
  built in `prepare`, outside timing.

## Timing

GPU time by CUDA-graph replay: the call (adding into a preallocated output, `mode: add`) is captured
once with its prepared metadata; each repetition replays it back to back (`graph_replays` 20), with
a 256 MiB L2 flush inside the graph and its replay time subtracted. Part 1: `bench/run_sweep.py`
(through `bench/run_mixed_sweep.py`), 30 repetitions, median and p20 / p80 per row, flush timed per
repetition. Part 2: `bench/run_multi_sweep.time_graph` (through `bench/run_multi_mixed_sweep.py`), 7
repetitions, flush timed once per call (median of 5). Warmup 10.
